**本轮目标（L1 本轮追加）**

执行令的四条判据里，API 前两条已随 `69ef28e` 合入并通过抽查。本轮补齐后两条，并把"进程管理"当成一个可复跑的证据链，而不是一次性手工点一遍：

1. `cd app && pnpm.cmd dev` 开窗口，窗口显示后端状态；
2. 杀掉 Python 后，窗口提示"后端断开"；
3. 退出客户端能回收子进程（含 Electron 被强杀这种异常退出）。

**顺带修掉的两个真问题**

其一，`python -m pipeline.api` 在 Windows 上根本起不来：`UnicodeEncodeError: 'charmap' codec can't encode`。原因是控制台默认 cp1252，`print` 一句中文就把服务打死。已改成启动时把 stdout/stderr 重设为 UTF-8（`errors="replace"`）。

其二，`.venv\Scripts\python.exe -m pipeline.api` 会再 spawn 一个系统 python，**真正监听 8765 的是孙进程**。任何只杀父进程的写法都会留下孤儿占端口。本轮所有关停改成按进程树杀，并加了一层父进程看门狗兜异常退出。

## 三、红绿验证

**红 1：拆掉"后端断开"推送**

把 `handleBackendExit` 里的断开推送和探活失败分支的推送同时注释掉，窗口在后端已死的情况下应停在"已连接"。实跑 `node scripts/verify-ui.mjs`：

```

[PASS] 手动杀掉后端进程树
[FAIL] 窗口提示后端断开 — {"state":"dot connected","label":"后端已连接",...}
== 结果：1 项未通过 ==
```

失败点正是要守的那条：**进程死了但界面还显示已连接**。恢复后同一条变绿。

**红 2：让 `/api/tools` 恒报成功**

把 `"ok": catalog.error is None` 改成 `"ok": True`：

```
FAILED tests/test_api.py::test_tools_missing_layer_reports_reason - assert True is False
FAILED tests/test_api.py::test_health_survives_broken_tools - assert True is False
2 failed
```

恢复后 12 项全绿。

**一个反直觉的观察，值得记一笔**

把"按树杀"（`taskkill /T`）去掉，只杀父进程，`verify-process.mjs` **仍然是绿的**；再把后端的父进程看门狗一起关掉，还是绿的——因为 `.venv` 的 launcher 与系统 python 之间存在句柄继承/等待关系，父进程被 `TerminateProcess` 后子进程也会退出。

结论不是"树杀没用"，而是：**这层保护有冗余**。所以本轮不把"单拆某层必红"当成验收标准；真正守住的是断言本身（杀完之后端口必须空、进程表里不许有 `pipeline.api`）。要制造红，得直接破坏断言目标（红 1 那样），而不是拆某一层实现。

## 五、文档摘要

- `app/README.md`（本轮新增）：跑法、两条验证命令、两个必须知道的坑（Windows 要按树杀；Electron 被强杀靠后端看门狗自尽）。
- `docs/并发分工.md`：本轮只读。L3 的交付判据现在四条全部可复跑。
- `coordination/README.md`：本件按六节格式落盘，文件名 `L3-交回-API与客户端-1616.md`。

**与执行令的偏差（请 L1 确认）**

1. **没用 `guasam/electron-react-app` 模板。** 理由：本轮验收只看进程管理与一个状态页，引入 React/Vite/Tailwind 会把变量从"进程有没有收干净"变成"前端构建链通不通"。现方案依赖只有 `electron` 一个，`pnpm.cmd dev` 等效于 `electron .`，窗口直接读 IPC。后续真做界面时再引构建链，`preload.js` 的白名单接口不用改。
2. **`/api/health` 字段比执行令多。** 执行令写 `{"ok", "version", "tools"}`，实现是 `ok/status/service/version/tools/pid/uptime_s`。多出来的 `pid` 是给进程管理取证用的（能对上 `taskkill` 的 PID），`status` 保留是为了兼容首轮已合入的响应。
3. **L2 缺失时 `/api/tools` 回 200 而不是 500。** 执行令说"先返回空列表"。实现是 `200 + ok=false + error`，比"空列表"多一句人话原因，界面能直接显示"工具层未就绪"。L2 已交付，实测 `ok=true/count=5`。
4. **`app/pnpm-workspace.yaml` 必须存在。** pnpm 11 把 `onlyBuiltDependencies` / `allowBuilds` 从 `package.json` 挪到了这里；不写就装不下 electron 二进制。这是环境约束，不是设计选择。

**设计要点（给后续接手的人）**

- `backend-service.js` 不依赖 electron，所以进程管理能在无窗口环境下被脚本反复验证。
- 状态有四个：`starting` / `connected` / `disconnected` / `stopped`。`stopped` 只在主动关停时出现，用来和"意外断开"区分。
- 探活 3 秒一轮；主进程 `before-quit` 里先 `stop()` 再 `app.exit()`，`process.on("exit")` 再兜一次同步 `taskkill /T`。

## 六、自检与遗留

**已验证**

- `pnpm.cmd dev` 开窗、显示后端地址与版本；后端未起时显示"启动失败"而不是白屏。
- 手动杀掉 Python（连孙进程）后，窗口 3–6 秒内变"后端断开"，截图与 DOM 文字均已取证。
- 正常退出（关窗口 → `window-all-closed` → `app.quit` → `before-quit` → `stop`）：进程表清零、端口释放。
- 异常退出（强杀 Electron）：后端看门狗 2 秒内自尽，端口释放。
- `pytest tests` 46 项全绿；`pipeline/api` 未改 harness / tools。

**未验证**

- macOS / Linux 路径（`detached: !IS_WINDOWS` + 进程组 `kill(-pid)` 已写，未实跑）。
- 打包分发（`electron-builder` 未接，本轮只跑源码目录）。
- 端口 8765 被**别的程序**占用时的表现：目前会显示"启动失败：未响应"，没有做端口占用探测与换端口。

**遗留与风险**

1. **单实例未做。** 同时开两个客户端，第二个会连上第一个的后端（探活成功即认为可用），退出第二个时不会杀它——因为 `stop()` 杀的是自己 spawn 的 PID。影响可控但会误导人，建议下一轮加 `app.requestSingleInstanceLock()`。
2. **退出清理最长 8 秒。** `stop()` 会等端口释放，最坏情况关窗要等 8 秒才退。可以改成"杀完就退、后台再确认"。
3. **看门狗有 2 秒窗口期。** 强杀 Electron 后，最多 2 秒内 8765 仍被占用；立刻重启客户端可能撞端口。真遇到时重试即可。
4. **`/api/tools` 每次请求都重新 `build_registry()`。** 五个工具、纯内存，开销可忽略；如果以后工具带初始化副作用，要改成进程级缓存。health 也每 3 秒调一次，同理。
5. **界面只是状态页。** 没有工具列表页、没有审批弹窗。工具清单接口已就绪（`/api/tools` 带 `risk` / `critical`），下一轮直接消费。
6. **`app/.verify/` 截图不入库。** 复核时如果看不到图，本地跑一次 `pnpm.cmd verify:ui` 会重新生成。
7. **pnpm 构建白名单是本机全局配置的一部分。** 换机器首次 `pnpm install` 可能仍被拦，报 `ERR_PNPM_IGNORED_BUILDS`，按提示 `pnpm approve-builds` 选 electron 即可；`app/pnpm-workspace.yaml` 已把这一步写进仓库，正常情况下不用手动点。
