**已验证**

- 三档闸门矩阵与文档一致；发布在 auto 档也必停；读类在 step 档也放行。
- 填稿/发布命令通过 subprocess 构造，参数、草稿路径、账号、`--confirm` 均有测试锁定。
- 工具层没有 import `patchright`，也没有 import `pipeline.content.headline`。
- `write_draft` 的 `critical=False` 已与 L1 对齐，不改。

**未验证（需要真实环境，单测刻意不覆盖）**

- 真实网页抓取（网络、反爬、编码）。
- 真实模型写稿（需要 `config.toml` 的 `[model]`）。
- 真实 ComfyUI 出图（需要本地服务与 checkpoint）。
- 真实头条登录、填稿、发布的端到端流程（需要 sau venv + patchright + 扫码）。

**遗留与风险**

1. **解释器必须指对**：默认 `sys.executable` 是本项目 venv，里面没有 patchright。真跑填稿/发布要设 `AIDIANSHANG_PYTHON=D:\social-auto-upload\.venv\Scripts\python.exe`，否则 CLI 会按 `headline.py` 的提示报“找不到 patchright”。
2. **填稿窗口的存活依赖人**：`headline.fill` 末尾有 `input()` 等回车。若从 API/后台以无 stdin 方式调，`input()` 收到 EOF 会立刻关浏览器，填好的内容就没了。真接 API 时，填稿应保留给人操作的终端/可见会话，或后续给 subprocess 显式保留 stdin；这一步在 L3/L1 接线时处理，L2 不擅自改 `headline`。
3. **发布成败是启发式**：`ok = returncode == 0`，且输出里出现“没找到确认按钮”时强制判失败；最终是否发出去以头条后台为准，结果里带 `note` 提醒。脚本输出格式变化会影响这条判断。
4. **发布脚本不在 L2 路径内**：`publisher.py` 只调用 `scripts/publish_toutiao.py`；如果脚本改参数名（`--draft/--account/--confirm/--wait`），这里要同步。
5. **临时草稿不长期保存**：内存草稿写在系统临时目录，路径随结果返回；需要留档时应由上层把草稿先落盘再传 `draft_path`。
6. **没有 `input_schema`**：目前由 LangChain 从函数签名推断；若之后要对模型做严格约束，再补 pydantic schema。
7. **账号去重不在工具层**：同一头条号被存成两个账号的拦截在 `headline._commit_login`，工具层只透传 `account`。

**publish 这个桩怎么接人工发布**

现在的实现是“命令构造器 + 硬闸门”，人工确认分两层：

1. **策略层**：`publish` 的 `Risk.IRREVERSIBLE` 让 `AutonomyController.needs_approval()` 无条件返回 True，任何档位（含 auto）都先抛 `ApprovalRequired`，`tool_args` 里带 `draft_path` / `draft` / `account`。也就是说，模型自己点不动发布。
2. **执行层**：人工批准后，subprocess 才跑 `publish_toutiao.py --confirm`。脚本用 patchright 开**可见**浏览器，依次填稿 → 点“预览并发布” → 等 `--wait` 秒 → 点“确认发布” → 截图 `pub-1/2/3`。全程人能看见、能接手，不是 headless。

推荐接法（半自动，符合头条“最后一下由人点”的原始设计）：

1. Agent 先调 `fill_editor`，在 standard 档停下，人批准后浏览器打开、稿子填好。
2. 人在浏览器里改稿、选封面/分类、加话题。
3. 人可以选择**直接在浏览器里点发布**——这时拒绝 `publish` 的审批即可，工具不会执行任何不可逆动作，`controller` 也不会记一次发布。
4. 也可以批准 `publish`，由脚本代点确认；工具返回 `ok/returncode/output/note`，发布后以头条后台为准核对。

API/桌面端接线时的落点：捕获 `ApprovalRequired`，从 `exc.tool_args` 取出草稿标题/正文做预览，弹确认框；用户点“批准”后再执行 `publisher.publish(**exc.tool_args)`（或由 L1 在 policy 层提供一次性放行令牌）。当前 `registry.call()` 会再次拦截，这是有意的；一次性放行属于 L1 的策略边界，L2 不越界实现。
