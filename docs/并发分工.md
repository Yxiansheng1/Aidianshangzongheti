# 并发分工：三条线，互不碰同一批文件

> 定这份的原因是：并发不是"开越多越快"，而是"文件不打架才快"。
> 每条线只改自己那几个目录，合流由主编排一个人做。

## 现在开三条，不要更多

| 线 | 负责 | 只允许改这些路径 | 交付判据 |
|---|---|---|---|
| **L1 harness**（已开工） | 智能体运行时、自主度策略、装配 | `pipeline/harness/**`、`tests/test_policy.py`、`tests/test_registry.py`、`scripts/harness_check.py`、`pyproject.toml` | `pytest` 全绿 + `scripts/harness_check.py` 输出三档闸门 |
| **L2 tools** | 把现有能力包成工具（含风险等级） | `pipeline/tools/**`、`tests/test_tools.py` | 5 个工具注册成功，`registry.describe()` 有风险等级，读类不审批、发布类必停 |
| **L3 api + 客户端** | FastAPI 薄壳 + Electron 壳（先做 API） | `pipeline/api/**`、`app/**`、`tests/test_api.py` | `GET /api/health` 通；`GET /api/tools` 能列出 L2 的工具清单 |

**为什么只开三条**：L2、L3 都依赖 L1 的接口（`ToolRegistry`、`AutonomyController`）。再多开一条线，就会有人去改 L1 的文件，冲突成本超过并行收益。

## 共享文件：只有主编排能改

```
pyproject.toml      L1 拥有
.github/**          主编排
docs/**             主编排（除非某条线写自己的 ADR，先登记路径）
config.toml         谁都不改
```

## 每条线的开工句（新会话直接贴）

**L2 tools**
> 你负责 L2：把现有 pipeline 能力包成工具。只改 `pipeline/tools/**` 和 `tests/test_tools.py`。
> 用 `pipeline.harness.registry.ToolRegistry`，给每个工具标 `Risk`（read/write/irreversible）和 `critical`。
> 先做这五个：抓原文、写稿、出图、填进头条编辑器、发布。填稿和发布要调现有 CLI（subprocess），不要 import patchright。
> 自测：`pytest tests/test_tools.py -q` 全绿；不许改 `pipeline/harness/**`。

**L3 api + 客户端**
> 你负责 L3：只改 `pipeline/api/**` 和 `app/**`。
> 目标：`python -m pipeline.api` 起一个本地 FastAPI（默认 127.0.0.1:8765），提供 `/api/health`、`/api/tools`（读 L2 的注册表）。
> 客户端先不做界面，先验证 Electron 主进程能拉起这个 Python 服务、退出时能杀掉。
> 不许改 `pipeline/harness/**` 和 `pipeline/tools/**`。

## 合流规则（防止乱）

1. 一条线跑通自己的判据后，**把改动清单发给主编排**，由主编排合并，不许自己合并到 main。
2. 每条线一个分支：`feat/harness`、`feat/tools`、`feat/console`。
3. 每次合并前主编排跑一次全量 `pytest`，绿了才合。
4. 跨线要改别人文件时，**先在这里登记**，不要直接改。
