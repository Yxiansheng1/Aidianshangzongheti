# 架构重构方案（自用工作台 · 电商 + 自媒体并行）

> 目标：把现在"一锅粥"的项目，改成**一个底座、两条线、五个台**。
> 前提：自用，单用户，不需要权限系统。
> 原则：**不推倒重来**，每步都能验收、都能用。

---

## 一、要解决的问题（现状证据）

| 现象 | 证据 | 后果 |
|---|---|---|
| 一个能力两份实现 | `pipeline/writer.py`（电商改写）与 `pipeline/content/rewrite.py`（自媒体改写） | 改一处另一处不动 |
| 界面平铺 | `ui.html` 80KB，8 个页签（analyze/gen/pick/queue/trend/writer/pub）挤一页 | 电商和自媒体混在一起 |
| 平台适配散落 | 头条 `content/headline.py`、百家号 `content/baijiahao.py`、其余 8 平台走 sau、映射表在 `content/publish.py` | 加一个平台要改 4 处 |
| 没有实体 | 产物散在 `output/内容/<时间戳>/`、`output/_state/`、`cookies/`、json | 找不回、复用不了、统计不了 |
| 探针堆积 | `scripts/` 46 个文件，其中约一半是一次性排查脚本 | 分不清哪些是工具 |

**根因**：能力、业务线、平台、界面四层压在同一层，每加一个功能要在每层各改一遍。

## 二、目标结构

```
┌─ ① 控制台 console ────────────────────────────────┐
│  内容台   电商台   发布台   账号台   数据台          │
│  （每台只读自己那条线的数据，互不干扰）              │
└───────────────┬──────────────────────────────────┘
                │ 调用业务线，不碰平台细节
┌─ ② 业务线 lanes ─────────────────────────────────┐
│  内容线：选题 → 取材 → 写 → 审 → 配图 → 发 → 收数据 │
│  电商线：找品 → 评分 → 素材 → 上架资料 → 分发 → 收数据│
└───────────────┬──────────────────────────────────┘
                │ 只调能力
┌─ ③ 能力 capabilities ────────────────────────────┐
│  fetch 取材 · write 写作 · image 出图 · video 视频  │
│  review 审核 · publish 发布 · metrics 采数          │
│  （每个能力：一个接口，多个实现，可替换）            │
└───────────────┬──────────────────────────────────┘
                │ 平台差异只允许出现在这一层
┌─ ④ 驱动 drivers ─────────────────────────────────┐
│  头条 · 百家号 · 小红书 · 抖音 · 快手 · 知乎 …      │
│  统一接口：login / open_draft / fill / publish /   │
│            check / list_posts                      │
└───────────────┬──────────────────────────────────┘
                │ 读写
┌─ ⑤ 底座 core ────────────────────────────────────┐
│  实体：Account 账号 · Persona 人设 · Topic 选题     │
│        Asset 素材 · Post 稿件 · Listing 商品       │
│        Metric 数据                                 │
│  存储：data/app.db（SQLite）+ data/assets/（文件）  │
└──────────────────────────────────────────────────┘
```

### 两条纪律

1. **平台差异不许漏到上层**。「头条没有发布接口、只能填稿，发布要人点」这种知识，只写在头条驱动里，业务线和界面不该知道。
2. **一个能力只留一份实现**。电商文案和自媒体稿子是同一个「写」能力的两组参数，不是两套代码。

## 三、实体（底座长什么样）

```python
Account(
    id, platform,            # toutiao / baijiahao / xiaohongshu ...
    name,                    # main / second
    label,                   # 号1 老韩读报
    identity,                # 平台上的真实身份（user_id / 百家号 id）
    state_path,              # 登录态文件
    persona_id,              # 这个号用哪个人设
    status,                  # ok / need_profile / need_realname / expired
)

Persona(id, name, tone, topics, card_path)      # 现在 output/人设-新闻/N1 那套

Topic(id, lane, source, title, url, keywords, heat)

Asset(id, lane, kind,        # image / video / text
      path, prompt, source_url, ai_generated, created_at)

Post(id, lane, account_id, topic_id, platform, skill, mode,
     title, body, tags, assets, status,
     # status: draft → reviewed → filled → published → failed
     published_url, published_at)

Listing(id, product, price, cost, score, assets, channels, status)
Metric(post_id, date, views, likes, comments, follows)
```

目录：

```
data/
  app.db                 # 索引与实体
  assets/内容/2026-11/   # 图片、视频
  assets/电商/2026-11/
  exports/               # 上架包、发布清单
output/                  # 历史产物保留，逐步导入索引，不删
```

## 四、迁移步骤（每步可验收）

| 步骤 | 做什么 | 工作量 | 验收标准 |
|---|---|---|---|
| 0 | 开分支 `refactor`，把当前能用的功能打 tag | 10 分钟 | 随时能切回老版本 |
| 1 | 建 `pipeline/core`：实体 + SQLite + 目录规范；把现有 `output/` 历史产物扫进索引 | 半天 | `python -m pipeline.core.index` 能列出所有历史稿件 |
| 2 | 建 `pipeline/drivers`：抽象统一接口；先搬**头条**和**百家号** | 1 天 | 用驱动跑通一次"填稿"，行为与现在一致 |
| 3 | 建 `pipeline/capabilities`：把 `writer.py` 与 `content/rewrite.py` 合成一个 `write`；`review` 合成一个 | 1 天 | 两条线调同一个函数，参数区分 |
| 4 | 拆控制台：一个壳 + 5 个台，先做「内容台」「账号台」 | 1–2 天 | 打开只有内容相关，不再看到选品按钮 |
| 5 | 把百家号/视频/上架包等接回新结构 | 按需 | 功能不丢 |

**顺序不可颠倒**：先有底座，东西才有地方放；先拆界面，底层没变就只是换皮。

## 五、两条线并行怎么不乱

并行不等于同时推进所有功能，而是**各自有固定节奏、共用底座**：

| | 内容线 | 电商线 |
|---|---|---|
| 每周节奏 | 两个号每天 1 篇（周末可停） | 每周跑通 2 个品的上架包 |
| 共用 | 账号、素材库、发布通道、数据回收 | 同左 |
| 不共用 | 写作 skill / 人设 | 选品评分 / 商品资料 |

**同一周只允许一条线"加新功能"，另一条只"按节奏跑"。** 这条纪律比架构更重要——之前乱，一半是因为每周都在两条线上同时加东西。

## 六、后续想加的功能，放哪一层

| 想要的功能 | 落在哪 | 说明 |
|---|---|---|
| AI 作图 / 仿爆款主图 | `capabilities/image` | 换实现即可，业务线不用动 |
| 模仿爆品文案 | `capabilities/write` 的一种模式 | 加一个 prompt 模板，不是新模块 |
| 选品雷达（自动找潜力品） | `capabilities/fetch` + 电商线的评分 | 复用取材能力 |
| 自动出短视频 | `capabilities/video` | 已有 ComfyUI Wan2.2 |
| 数据看板 | `console/数据台` + `capabilities/metrics` | 只读，不影响生产 |
| 多平台同步分发 | 各 `drivers` 完成即可 | 业务线只需循环账号 |

**判断标准**：如果新功能需要在四个层都改，说明它该被拆成"能力 + 业务线配置"，而不是一个新模块。
